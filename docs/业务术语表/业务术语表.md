## 1. 使用说明

1. 本表是**语义约定**，不替代需求文档；与 `docs/requirements/` 冲突时，以需求文档为准。
2. 术语定义优先描述**业务含义**，必要时补充系统表现（如“对应一条拟录取记录”）。
3. “明确不实现的业务”列出的词，用于防止开发或测试误实现需求边界。
4. 同一概念在全项目中使用统一叫法，具体见 §13“术语使用规范”。
5. 本文中的“系统”指实训室选拔系统；“线下”指系统之外实际发生的宣讲、走访、面试、调剂讨论和入组。

### 1.1 核心概念关系

```
学生 ──填报──> 志愿申请 ──包含──> 志愿目标 ──导师发放──> 拟录取 ──学生确认──> 最终录取
导师 ──维护──> 实训室信息 ──计划招收人数──> 发放拟录取
负责人 ──配置──> 阶段 ──可选生成──> 阶段调整公告
```

- 三个角色共享阶段、公告、个人待办和实训室公开信息。
- 学生与导师围绕“志愿申请 / 志愿目标 / 拟录取”发生业务关系。
- 最终录取是每名学生唯一的录取去向，可能来自志愿录取，也可能来自统筹调剂。

## 2. 角色与身份

| 术语 | 定义 |
| --- | --- |
| 用户 | 系统中可登录的主体。系统以 `(学工号, 角色)` 唯一标识一个用户身份；同一学工号选择不同角色会形成两个独立用户身份，不自动合并。 |
| 身份 | 学工号与登录时所选角色的组合，是权限判断和数据归属的依据。身份以登录时选择为准，不根据学工号推断。 |
| 角色 | 系统支持的三类角色：学生、导师、负责人。角色决定左侧菜单、接口路径前缀和数据权限。 |
| 学生 | 以“学生”身份登录的用户。主要操作：查看阶段与公告、填报志愿、上传简历、查看并确认拟录取、查看最终录取结果。 |
| 导师 | 以“导师”身份登录的用户。主要操作：填写/修改本人实训室信息、查看本人名下申请与简历、录入面试分数、同分排序、发放拟录取。 |
| 负责人 | 以“负责人”身份登录的用户。主要操作：配置各阶段起止时间、选择是否发布阶段调整公告；不参与学生志愿、导师发放等个人业务。 |
| 学工号 | 10 位数字，格式为 `^\d{10}$`，由四位年份 + 三位代码 + 三位序号组成。登录只校验格式，不查询账号是否存在，也不校验身份是否匹配。 |
| 姓名 | 用户展示名，来源为 `sys_user.name`。可为空；为空时页面显示学工号。登录页不要求输入姓名。 |
| 导师姓名 | 导师在“实训室信息”中填写的姓名，用于学生志愿的导师匹配。保存时去首尾空格、合并连续空格；与用户展示姓名 `sys_user.name` 可能不同，`sys_user.name` 也可能为空。 |
| 登录 | 选择身份、输入合法学工号、完成模拟人脸比对后进入系统。系统不提供注册、密码登录或找回密码；登录成功后销毁旧会话并新建会话。 |
| 模拟人脸比对 | 前端本地进行的格式校验与状态切换操作。格式正确即视为“比对成功”；不调用摄像头、不调用后端人脸服务、不上传或存储人脸数据。 |
| 会话 | 服务端保存的登录状态（HttpSession），包含 `userId`、`staffNo`、`name`、`role`。Cookie 使用 `HttpOnly`、`SameSite=Lax`、`Path=/`，生产环境 `Secure=true`，默认超时 30 分钟。 |
| 注销 | 使当前会话失效。前端清理用户状态并返回登录页。 |
| 当前用户 | 当前会话中的用户。所有个人数据查询和归属判断都以当前用户为准，绝不从请求参数或请求体读取 `userId`、`role`、`studentId`、`teacherId` 作为身份依据。 |
| 权限 | 两层控制：路径级角色约束（`/student/**`、`/teacher/**`、`/manager/**`）+ Service 层数据归属校验。 |
| 数据归属 | 个人数据只能由本人或被授权的角色访问。例如导师只能查看投递到本人名下的申请，学生只能查看本人的志愿、拟录取和最终录取。 |
| 越权 | 访问不属于当前用户的数据。系统返回 HTTP 403 + `code=40301`，提示“无权访问该数据”。 |
| 角色菜单 | 按当前会话角色渲染的左侧功能菜单。系统不提供顶栏角色切换；切换身份必须退出后重新登录。 |
| 已录取学生 | 已形成最终录取的学生。主页面显示“已录取”和最终实训室/导师；不再生成志愿填报、补录、拟录取确认待办；点击“志愿填报”只提示“已被录取！”。 |
| 未录取学生 | 没有最终录取的学生。可按规则参加后续轮次、补录或统筹调剂；最终未获接收的由负责人线下处理。 |

## 3. 选拔流程与阶段

| 术语 | 定义 |
| --- | --- |
| 选拔 | 软件学院实训室选拔学生的完整流程：集中宣讲 → 实训室开放日 → 第一轮录取 → 第二轮录取 → 第三轮录取 → 统筹调剂 → 正式入组。 |
| 选拔阶段 | 选拔流程中的固定阶段。系统配置为 7 行：集中宣讲、实训室开放日、第一轮录取、第二轮录取、第三轮录取、统筹调剂、正式入组。阶段名称和顺序固定，不可新增、删除或重命名。 |
| 阶段编码 | 固定英文编码：`BRIEFING`、`OPEN_DAY`、`ROUND_1`、`ROUND_2`、`ROUND_3`、`ADJUSTMENT`、`ENROLLMENT`。用于系统识别，不面向用户展示。 |
| 阶段配置 | 负责人为 7 个阶段设置起止时间。保存后立即生效；更新原配置，不保留历史版本。 |
| 阶段时间 | 某一阶段的开始时间和结束时间。精确到分钟；必填；开始必须早于结束；按流程顺序且不能重叠；阶段之间允许留空档。 |
| 当前阶段 | 服务端当前时间落在其起止区间内的阶段。时间落在两个阶段之间时显示下一阶段及开始时间；全部阶段结束后显示“选拔已结束”；尚未配置时显示“阶段暂未配置”。 |
| 阶段空档 | 前一阶段结束到后一阶段开始之间的时间间隔。允许存在；空档期间显示下一阶段及开始时间。 |
| 阶段暂未配置 | 7 个阶段尚无完整的起止时间。主页面不虚构当前阶段和倒计时，阶段管理页展示空白表单。 |
| 选拔已结束 | 全部阶段结束后的状态。主页面不再显示当前阶段和倒计时。 |
| 集中宣讲 | 选拔的第一个阶段，面向全体学生，线下进行。系统只展示阶段和公告，不提供线上宣讲排期、签到或直播。 |
| 实训室开放日 | 选拔的第二个阶段，面向全体学生，线下走访进行。系统只展示阶段和公告。 |
| 第一轮录取 | 第一轮“志愿填报 → 面试 → 拟录取确认”。系统为该轮配置统一开始/结束时间，不单独拆分子阶段时间。 |
| 第二轮录取 | 第二轮录取，流程同第一轮。仅尚未录取的学生参加；按剩余名额重新填报；补录沿用志愿填报页面。 |
| 第三轮录取 | 第三轮录取，流程同第一轮。仅尚未录取的学生参加；三轮结束后不再安排第四轮填报。 |
| 三轮录取 | 第一轮、第二轮、第三轮的统称。主页面展示时作为一个顶层阶段，阶段管理中展开为三轮分别配置起止时间。 |
| 轮次 | 录取轮次编号 1 / 2 / 3。每轮包含志愿填报、面试、拟录取确认，三者共用该轮起止时间。 |
| 正式入组 | 选拔流程的最后阶段。实际入组在线下进行；系统只展示阶段，不提供线上入组操作。 |
| 统筹调剂 | 第三轮结束后，仅处理仍未录取学生的线下调剂。依据学生最后一次成功提交的调剂意愿、面试分数和剩余名额安排；线上只展示结果，不提供学生确认或导师接收操作。 |
| 阶段调整 | 负责人修改阶段起止时间。保存后立即生效；不恢复已放弃的拟录取、不重新开放已截止的填报/确认、不回滚已提交的志愿和录取结果。 |
| 阶段调整公告 | 负责人保存阶段时可选生成的公告。首次配置时列出全部阶段；后续修改只列出本次变更的阶段，并展示原时间与新时间。每次保存最多生成一条；发布后不可修改/删除。 |

## 4. 实训室与简历

| 术语 | 定义 |
| --- | --- |
| 实训室 | 导师开展选拔的实训场所。系统不建共享的实训室主数据；实训室名称和位置由导师在本人信息中自行填写，不要求负责人预先配置。 |
| 实训室信息 | 导师本人填写的实训室名称、位置、计划招收人数、导师姓名、研究方向、联系方式及导师简历。学生可查看；仅导师本人可修改。 |
| 研究方向 | 导师填写的方向文本，例如“云计算与大数据”。学生可在实训室列表中按研究方向筛选。 |
| 联系方式 | 导师填写的联系电话等文本，在实训室详情中展示。 |
| 计划招收人数 | 导师本人计划招收的学生总数，必须为正整数。该人数跨三轮累计，不是每轮独立名额。 |
| 实训室总计划人数 | 同一实训室下所有导师计划招收人数之和。系统不单独存储，按实训室名称（可结合位置）汇总；同一实训室不重复填写总额。 |
| 导师简历 | 导师上传的 PDF 简历，用于学生查看导师信息。所有已登录用户可下载。 |
| 学生简历 | 学生上传的 PDF 简历，用于导师查看申请。仅学生本人和收到该申请的导师可下载。 |
| 简历文件 | 系统保存的 PDF 文件及其元数据（所有者、用途、原始文件名、大小、路径等）。文件存放在 Web 根目录之外，不映射为静态资源。 |
| 文件 ID | 上传接口返回的 `fileId`。提交志愿或实训室信息时只传 `fileId`；服务端校验文件属于当前用户且用途匹配。 |
| 鉴权下载 | 通过带登录会话的下载接口获取简历，而不是直接访问 `uploads/` 目录。下载时校验文件用途和访问者归属。 |
| PDF | 系统唯一接受的简历格式。校验扩展名 `.pdf`、Content-Type `application/pdf`、文件头 `%PDF-`；大小默认上限 10 MB。 |
| 原始文件名 | 用户上传时的文件名。仅用于页面展示和下载时的文件名，不作为磁盘文件名；磁盘名使用 UUID。 |
| 上传 | 将 PDF 保存到磁盘并写入简历元数据。上传失败不产生半条数据库记录。 |
| 替换简历 | 重新上传并更新实训室信息或志愿中的简历引用。旧文件若仍被历史记录引用则保留；孤立文件清理后置。 |

## 5. 志愿与补录

| 术语 | 定义 |
| --- | --- |
| 志愿填报 | 学生在某一轮填写 1–3 名意向导师姓名、选择两项调剂意愿、上传 PDF 简历后提交本人的志愿申请。 |
| 志愿申请 | 一名学生在一轮内的一份申请。每生每轮一份；不同轮次独立保存，不覆盖上一轮志愿及处理结果。 |
| 志愿目标 | 志愿申请经导师姓名解析后形成的一个导师目标。一个申请最多 3 个目标；面试分数和同分顺序保存在目标上。 |
| 平行志愿 | 1–3 名导师志愿不区分优先级，不是“第一志愿 / 第二志愿 / 第三志愿”的梯度关系；三个输入框地位相同。 |
| 志愿导师 | 学生填报并被系统解析到的一名导师。 |
| 导师姓名解析 | 服务端对学生输入的导师姓名去首尾空格、合并连续空格后，与实训室信息中的导师姓名精确匹配。必须匹配到唯一一名导师，否则拒绝提交。 |
| 重名 | 多个导师具有相同的规范化导师姓名。系统无法确定学生意向，提交时拒绝并提示“导师姓名不存在或存在重名，请联系负责人”。 |
| 调剂意愿 | 志愿申请中的两项选择：“是否同意实训室内调剂”和“是否同意学院内调剂”。每项必须选择“同意”或“不同意”；均选择“不同意”也可以提交。统筹调剂采用学生最后一次成功提交的志愿申请中的两项意愿，不强制使用第三轮数据。 |
| 实训室内调剂 | 统筹调剂中的优先层级。由学生最后一次志愿中导师所在的实训室讨论是否接收；接收后直接形成调剂录取，不再要求学生确认。 |
| 学院内调剂 | 跨实训室的调剂。实训室内未接收且学生同意学院内调剂，或学生不同意实训室内但同意学院内调剂时进入；接收后直接形成调剂录取。 |
| 志愿重填 | 在同一轮内再次提交志愿，替换本轮志愿目标，不新增第二条申请，不影响其他轮次。已进入评分/发放阶段的轮次不可重填（设计约束，见接口文档待确认项）。 |
| 分轮补录 | 第二、第三轮为尚未录取学生开放的再次填报机会。复用“志愿填报”菜单和页面，不新增独立补录菜单。 |
| 补录页 | 志愿填报页在第二、第三轮的补录模式。顶部只读展示仍有剩余名额的导师列表，下方仍使用三个普通导师姓名输入框，不出现搜索框或可点击候选列表。 |
| 剩余名额导师列表 | 当前轮仍有剩余名额的导师只读列表，至少包含导师姓名、所属实训室及剩余名额。仅用于查看，不改变填报方式。 |
| 补录名额 | 当前轮仍有剩余名额的导师所提供的可补录名额。没有剩余名额时提示“本轮暂无可填报名额”。 |
| 补录开放时间 | 第二、第三轮各自的起止时间。未开始提示“补录填报尚未开始”；已截止提示“补录填报已截止”。 |
| 补录截止 | 当前轮结束时间。截止后不能提交补录。 |
| 已录取不可填报 | 已有最终录取的学生不能提交志愿或补录；即使使用旧页面提交，也会被服务端拒绝。 |
| 收到拟录取但未确认 | 学生收到状态为“待确认”的拟录取，但尚未确认。该状态不视为已录取；在轮次和时间允许的情况下，仍可按规则参加后续填报。 |
| 每轮独立 | 第一、第二、第三轮的志愿、简历、调剂意愿和处理结果分别保存；新一轮填报不覆盖上一轮。 |
| 历史轮次 | 已经结束的轮次。记录保留，可查询，不参与当前轮的填报、评分或发放操作。 |

## 6. 面试、名额与发放

| 术语 | 定义 |
| --- | --- |
| 面试 | 导师在线下对申请本人名下的学生进行的面试。系统不提供面试排期、签到或线上会议，只提供面试分数录入。 |
| 面试分数 | 导师对某条志愿目标录入的评分，范围 0–100，允许两位小数。未评分的目标不参与排序和发放。 |
| 面试结果 | 导师对某条志愿目标的面试评分与同分顺序。系统将其保存在志愿目标上，不单独建面试结果表。 |
| 评分 | 导师录入或修改面试分数的操作。已产生拟录取的目标不可再修改分数（设计约束）。 |
| 未评分 | 面试分数为空。未评分学生不参与发放。 |
| 已评分 | 面试分数非空。已评分学生参与排序和达标判断。 |
| 同分 | 同一导师、同一轮内多个学生的面试分数相同。 |
| 同分排序 | 对同分学生由导师手动确定先后顺序，系统不随机排序。未定序时，相关发放暂停。 |
| 手动定序 | 导师为同分学生设置先后顺序（`tieOrder`），数字越小越靠前。 |
| 录取分数线 | 导师点击发放时设置的最低面试分数。面试分数大于或等于分数线的学生才有资格收到拟录取；分数线不是固定配置，也不降低或超额发放。 |
| 达标学生 | 已评分、面试分数 ≥ 录取分数线、没有最终录取、没有拟录取、且同分顺序已确定的学生。 |
| 名额 | 导师可招收的学生数量，以计划招收人数为上限。日常语境中的“名额”通常指剩余可发放名额。 |
| 计划名额 | 导师的计划招收人数，跨轮次累计的总数，不是每轮独立名额。 |
| 已占用名额 | 导师已形成的最终录取数（含志愿录取、调剂录取）+ 未过确认截止时间的待确认拟录取数。 |
| 待确认名额 | 状态为“待确认”的拟录取所占用的名额。超时未确认或确认其他导师后释放（这两种情况统称学生放弃）。 |
| 剩余名额 | 计划名额 − 已占用名额。用于判断能否发放、能否补录，以及补录页导师列表。 |
| 名额概览 | 导师发放页顶部展示的“计划名额 / 已确认 / 待确认 / 剩余可发放”摘要。 |
| 发放拟录取 | 导师按面试分数从高到低、结合录取分数线和剩余名额，在系统内生成拟录取记录。系统不发送短信、邮件或站内推送。 |
| 递补 | 学生放弃（超时未确认或确认其他导师）导致名额释放后，在本轮截止前按顺序向下一名达标学生发放拟录取。 |
| 超发 | 发放的拟录取数量超过剩余名额。系统禁止，通过事务、行锁和唯一索引兜底。 |
| 重复发放 | 同一导师在同一轮向同一学生多次发放拟录取。系统禁止。 |
| 未达标 | 面试分数低于录取分数线，或尚未评分，不能获得拟录取。 |
| 已发放 | 已生成拟录取记录的学生或目标。已发放目标的面试分数和同分顺序不可再修改（设计约束）。 |

## 7. 拟录取与最终录取

| 术语 | 定义 |
| --- | --- |
| 拟录取 | 导师向学生发出的拟录取记录，表示愿意录取该学生。记录包含导师、实训室、轮次、状态和确认截止时间。 |
| 拟录取通知 | 拟录取记录在学生端的展示名称。发放拟录取即生成记录，学生登录后查看；不是短信、邮件或纸质通知。 |
| 拟录取确认 | 学生在确认截止时间前主动确认一条拟录取。系统不自动确认；即使只收到一条，也必须主动确认。确认后不可更改，其余本人待确认拟录取自动放弃。 |
| 待确认 | 拟录取状态 `PENDING`。表示导师已发放、学生尚未确认；该记录占用导师名额，可在截止前确认。 |
| 已确认 | 拟录取状态 `CONFIRMED`。表示学生已确认该拟录取；系统形成志愿录取的最终录取；不可再更改。 |
| 已放弃 | 拟录取状态 `ABANDONED`。表示学生超时未确认或确认了其他导师；该记录释放名额，不可再确认。 |
| 超时放弃 | 到达确认截止时间仍未确认，系统自动将待确认拟录取改为已放弃，放弃原因记为 `TIMEOUT`。 |
| 确认截止时间 | 一条拟录取的确认截止时间。默认取发放时本轮结束时间，发放时写入记录；后续阶段调整不自动延长或改写该快照。 |
| 确认其他导师 | 学生确认某一条拟录取后，本人其余待确认拟录取自动放弃，放弃原因记为 `CONFIRMED_OTHER`。 |
| 自动放弃 | 由超时或确认其他导师触发的放弃，不是学生手动点击“放弃”。 |
| 最终录取 | 每名学生唯一的最终录取去向。可能来自志愿录取，也可能来自统筹调剂；系统以最终录取记录表示。 |
| 志愿录取 | 学生在第一、第二或第三轮确认某条拟录取后形成的最终录取。录取类型为 `VOLUNTEER`，关联轮次和来源拟录取。 |
| 调剂录取 | 三轮结束后通过统筹调剂形成的最终录取。录取类型为“实训室内调剂”或“学院内调剂”；没有轮次、没有来源拟录取，不需要学生确认。 |
| 调剂结果 | 统筹调剂形成的最终录取结果在学生端的展示名称；只读，不提供确认按钮，也不执行拟录取的超时放弃规则。 |
| 录取去向 | 学生最终录取的导师和实训室。每名学生最终只能有一个录取去向。 |
| 录取类型 | 最终录取的来源类型：志愿录取、实训室内调剂、学院内调剂。 |
| 录取状态 | 拟录取的状态：待确认、已确认、已放弃。最终录取不再区分状态，表示已确定的最终结果。 |
| 录取结果 | 学生端展示的最终录取信息，包括录取类型、导师、实训室、录取时间等。 |
| 已录取 | 学生已形成最终录取。主页面显示“已录取”；不再参加后续轮次、补录或拟录取确认。 |
| 未录取 | 学生没有最终录取。三轮结束后可进入统筹调剂，或由负责人线下处理。 |
| 唯一录取 | 每名学生最终只能有一个录取去向。系统以最终录取的唯一约束保证。 |

## 8. 公告与待办

| 术语 | 定义 |
| --- | --- |
| 公告 | 面向全体登录用户的只读通知。只能由阶段保存时生成；发布后不可修改、不可删除。 |
| 阶段调整公告 | 负责人保存阶段时可选发布的公告。内容由本次阶段变更生成，发布前可编辑；首次配置列出全部阶段，后续只列出本次变更阶段并展示原/新时间。 |
| 公告发布 | 将公告草稿写入公告列表并面向全体用户展示。公告发布在阶段保存成功之后用独立事务执行；发布失败不回滚阶段。 |
| 公告草稿 | 发布前自动生成、允许编辑的公告标题和正文。保存于阶段保存记录中，供发布失败后重试使用；未发布前不对普通用户展示。 |
| 公告只读 | 系统不提供公告新增、编辑、删除入口；没有公告管理页面或接口。公告只能由阶段保存生成。 |
| 公告发布失败重试 | 阶段保存成功但公告发布失败时，阶段仍生效；重试只发布公告，不重复保存阶段，也不重复生成公告。 |
| 公告列表 | 公告只读分页列表，展示标题、摘要和发布时间；点击进入公告详情。 |
| 公告详情 | 公告完整正文页面，只读。 |
| 公告摘要 | 由公告正文派生的列表摘要，不单独存储。 |
| 个人待办 | 与当前用户相关、当前可办理的事项。由“当前阶段 + 用户状态”实时推导，不单独建表，不缓存过期结果。 |
| 待办事项 | 一条具体待办，例如“填报志愿”“确认拟录取”“填写实训室信息”“录入面试分数”“发放拟录取”“配置阶段”。 |
| 可办理 | 在当前阶段和用户状态下允许操作，且尚未截止的事项。 |
| 截止时间 | 待办对应的截止时间。部分待办没有强制截止时间（如填写实训室信息），此时可为空。 |
| 已完成 | 已经办理的事项。不再作为待办展示。 |
| 已截止 | 已过截止时间的事项。不再作为可办理待办展示。 |
| 暂无待办 | 当前没有可办理事项的空状态。加载失败不能显示为“暂无待办”。 |
| 加载失败 | 数据请求失败的状态。页面显示“加载失败，请重试”，不能把失败当成空数据。 |
| 页面三态 | 每个页面必须处理的三种状态：加载中、空状态、加载失败。 |

## 9. 交互与状态

| 术语 | 定义 |
| --- | --- |
| 提交 | 将表单内容发送到服务端保存。成功和失败都有明确提示。 |
| 重填 | 在允许的轮次内再次填写并提交，覆盖本轮申请，不影响其他轮次。 |
| 提交中 | 请求正在进行。按钮禁用，防止重复提交。 |
| 提交失败 | 服务端拒绝或网络失败。保留已填内容和已上传的简历，允许修改后重试。 |
| 提交成功 | 服务端保存成功。显示成功提示；需要时刷新相关数据。 |
| 表单禁用 | 必填项不完整、格式不正确、上传未完成、提交中或状态不允许时，按钮不可点击。 |
| 表单启用 | 所有条件满足后，按钮可点击。 |
| 防重复提交 | 前端按钮禁用 + 服务端事务、状态判断、唯一索引三重兜底；按钮禁用只是 UX，不是唯一保障。 |
| 幂等 | 同一操作重复执行不会产生重复业务结果。系统通过唯一索引、事务和状态判断保证，例如重复确认、重复发放、重复保存阶段。 |
| 只读 | 只能查看，不能修改、删除或提交。公告、历史轮次记录、调剂结果等均为只读。 |
| 空状态 | 确实没有数据时的展示，例如“暂无公告”“暂无待办”“暂无拟录取”。 |
| 加载中 | 数据请求进行中的页面状态。 |
| 服务端时间 | 服务端当前时间。所有开放、截止、超时判断以服务端时间为准；接口返回 `serverTime`，前端计算本地偏移。 |
| 倒计时 | 基于服务端时间计算的剩余时间，不依赖浏览器时钟。 |
| 二次确认 | 对不可逆操作先弹出确认提示，例如确认拟录取前提示“确认后不可更改，其他拟录取将自动放弃”。 |
| Toast | 全局轻提示，用于成功、失败或警告文案；文案应与需求文档一致。 |

## 12. 易混淆术语对照

| 术语 A | 术语 B | 区别 |
| --- | --- | --- |
| 拟录取 | 最终录取 | 拟录取是导师发出的拟录取记录，可能被放弃；最终录取是每名学生唯一的最终去向。 |
| 拟录取通知 | 录取通知书 | 拟录取通知是系统内记录；系统不生成纸质/电子录取通知书。 |
| 已确认 | 已录取 | 已确认是某条拟录取的状态；已录取是学生已有最终录取的结果。 |
| 待确认 | 已录取 | 待确认只是收到拟录取，尚未确定去向；不视为已录取。 |
| 超时放弃 | 主动放弃 | 超时放弃由系统在确认截止后自动处理；需求中不提供学生主动放弃按钮。 |
| 确认其他导师 | 已放弃 | “确认其他导师”是放弃原因；已放弃是拟录取的终态。 |
| 志愿录取 | 调剂录取 | 志愿录取来自三轮内的拟录取确认；调剂录取来自三轮后的统筹调剂，不需要学生确认。 |
| 实训室内调剂 | 学院内调剂 | 实训室内调剂在最后一次志愿导师所在实训室内进行；学院内调剂跨实训室进行。 |
| 统筹调剂 | 实训室内 / 学院内调剂 | 统筹调剂是三轮后的整体线下调剂流程；后两者是该流程中的两个优先层级。 |
| 补录 | 递补 | 补录是第二、第三轮的再次填报机会；递补是本轮内有人放弃后向下一名达标学生发放。 |
| 补录 | 第二轮录取 | 补录是第二轮录取中的填报机会；第二轮录取是完整的“填报 → 面试 → 确认”轮次。 |
| 计划招收人数 | 剩余名额 | 计划招收人数是导师计划总数；剩余名额是计划总数减去已占用名额后的可发放数量。 |
| 已占用名额 | 待确认名额 | 已占用名额包含最终录取和待确认拟录取；待确认名额只是其中待确认的那部分。 |
| 面试分数 | 录取分数线 | 面试分数是学生的得分；录取分数线是导师发放时设置的最低门槛。 |
| 同分 | 同分排序 | 同分是分数相同的客观状态；同分排序是导师手动确定的先后顺序。 |
| 未评分 | 未达标 | 未评分是没有录入分数；未达标是未达到录取资格，通常指已评分但低于录取分数线。两者都不能发放。 |
| 已发放 | 已确认 | 已发放是导师生成了拟录取；已确认是学生接受了拟录取。 |
| 阶段 | 轮次 | 阶段是流程中的 7 个固定阶段；轮次是其中三轮录取的编号 1/2/3。 |
| 阶段调整 | 阶段历史版本 | 阶段调整是修改当前起止时间；系统不保留历史版本。 |
| 公告 | 阶段调整公告 | 公告是通用只读通知；阶段调整公告是阶段保存时生成的那类公告。 |
| 个人待办 | 公告 | 个人待办是当前用户可办理的事项；公告是面向全体用户的只读通知。 |
| 加载失败 | 暂无数据 | 加载失败是请求失败；暂无数据是请求成功但没有记录。二者不能混用。 |

## 13. 术语使用规范

| 统一使用 | 避免使用 | 说明 |
| --- | --- | --- |
| 学生 | 同学、考生、学员 | 角色名统一为“学生”。 |
| 导师 | 老师、教师、mentor | 角色名统一为“导师”。 |
| 负责人 | 管理员、admin、超级管理员 | 系统只有“负责人”角色，不使用“管理员”。 |
| 学工号 | 学号、工号 | 统一为“学工号”，指 10 位数字。 |
| 用户 / 身份 | 账号 | “账号”只在“不校验账号是否存在”等否定语境出现；业务文档优先用“用户/身份”。 |
| 实训室 | 实验室、机房 | 业务名称统一为“实训室”。 |
| 拟录取 | 录取通知、offer、录取意向 | 系统内记录统一称“拟录取”；“拟录取通知”可用于学生端展示名。 |
| 发放拟录取 | 发送录取通知、发 offer | “发放”指在系统内生成拟录取记录，不发送外部通知。 |
| 拟录取确认 | 接受录取、录取确认、接受 offer | 学生主动确认拟录取的动作。 |
| 最终录取 | 正式录取、最终去向 | 每名学生唯一的最终录取；“录取结果”可用于学生端展示，“正式入组”是线下阶段，不要混用。 |
| 志愿 | 报名、志愿项 | 学生填报的导师意向统一称“志愿”；一份完整记录称“志愿申请”。 |
| 志愿申请 | 报名表、申请表 | 每生每轮一份志愿申请。 |
| 志愿目标 | 志愿项、导师志愿 | 志愿申请解析后的单个导师目标。 |
| 补录 | 征集志愿、第二轮填报 | 第二、第三轮的再次填报统一称“补录”。 |
| 轮次 | 批次、阶段 | 录取轮次编号 1/2/3；不要与“阶段”混用。 |
| 阶段 | 环节、时期 | 7 个固定阶段；不要与“轮次”混用。 |
| 服务端时间 | 服务器时间、系统时间、北京时间 | 统一为“服务端时间”，是所有截止判断的依据。 |
| 确认截止时间 | 确认期限、截止日期、有效期 | 拟录取的确认截止时间，发放时写入快照。 |
| 计划招收人数 | 招生名额、计划人数、招生计划 | 导师本人填写的计划总数。 |
| 已占用名额 | 已用名额、已招人数 | 最终录取 + 未过截止的待确认拟录取。 |
| 剩余名额 | 余额、空余名额、可招人数 | 计划名额 − 已占用名额。 |
| 公告 | 通知、消息、推送 | 系统内只读通知统一称“公告”。 |
| 阶段调整公告 | 阶段公告、调整通知 | 阶段保存时生成的那类公告。 |
| 个人待办 | 任务、消息 | 实时推导的个人可办理事项；单条可称“待办事项”。 |
| 空状态 | 暂无数据（除非确实为空） | 加载失败不能写成“暂无数据/暂无待办”。 |
| 模拟人脸比对 | 人脸识别、刷脸、实名认证 | 统一为“模拟人脸比对”，强调不采集人脸数据。 |
| 线下 | 线上 | 宣讲、开放日、面试、调剂讨论、正式入组均在线下进行；线上只做记录与展示。 |

### 13.1 文案一致性提醒

- “名额已满”“请填写有效分数”“请先确定同分学生顺序”“暂无可发放的达标学生”“本轮拟录取发放已截止”等提示，以 `CLAUDE.md` §12.4 和接口文档为准。
- “阶段已保存，公告发布失败，请重试”表示**阶段已生效**，不是整体保存失败；前端应保留重试入口，不能提示“保存失败”。
- “你已确认录取，无需参加补录”和“已被录取！”用于不同入口：前者用于补录提交被拒绝，后者用于已录取学生点击“志愿填报”菜单。
- “补录填报尚未开始 / 补录填报已截止”用于第二、第三轮；第一轮的对应提示为“志愿填报尚未开始 / 志愿填报已截止”（接口文档新增，待产品确认）。
- “暂无拟录取”“暂无待办”“暂无公告”只在**请求成功且确实为空**时使用；加载失败必须显示“加载失败，请重试”。
