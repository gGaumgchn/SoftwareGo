# 实训室选拔系统 · 开发任务拆解

> 文档版本：v1.0  
> 编写日期：2026-11-16  
> 依据：`CLAUDE.md`、`docs/requirements/`、`docs/数据库设计/数据库设计.md`、`docs/接口设计/API接口设计.md`、`docs/业务术语表/业务术语表.md`  
> 目的：把需求拆成可执行、可验收、可并行的开发子任务，并给出推荐开发顺序。

---

## 1. 对你提出的顺序的判断

你提出的顺序：

1. 所有前端页面开发
2. 后端注册 / 登录接口实现
3. 后端核心功能实现
4. 前后端联调

### 1.1 总体结论

**大方向可以理解，但不建议按这个顺序执行。**

主要问题有三个：

1. **前端全量先行，容易返工。** 页面交互依赖大量业务规则（阶段是否开放、是否已录取、名额、同分、确认截止、公告失败重试等）。前端全部做完再写后端，会让这些规则在联调阶段才暴露，导致页面结构和状态逻辑返工。
2. **“联调”不应是最后一个阶段。** 如果最后才第一次联调，问题会集中爆发，难以定位是接口契约、数据模型、权限还是页面状态的问题。正确做法是**每个纵切功能完成后立即联调验收**。
3. **系统没有“注册”接口。** 需求明确不提供注册、密码登录和找回密码；首次登录时按 `(学工号, 角色)` 自动创建用户。因此第二步应表述为“**登录 / 会话 / 自动建用户**”，不是“注册 / 登录”。

### 1.2 逐项评价

| 你的步骤 | 评价 | 建议 |
| --- | --- | --- |
| 1. 所有前端页面开发 | 部分合理 | 可以先做前端脚手架、主题、布局、公共组件和静态页面结构；但**不要把所有页面业务逻辑做完再等后端**。业务页面应跟随后端纵切逐批完成并联调。 |
| 2. 后端注册 / 登录接口 | 合理，但需修正 | 没有注册接口。登录、会话、自动建用户应作为第一个纵切，和前端登录页、路由守卫、布局一起完成。 |
| 3. 后端核心功能 | 过于笼统 | 应按业务域拆成阶段/公告、实训室/文件、志愿/补录、评分/发放、拟录取确认、最终录取/调剂等纵切，每块后端 + 前端 + 测试 + 联调一起完成。 |
| 4. 前后端联调 | 顺序不合理 | 联调应贯穿每个纵切，最后阶段只做**全链路回归、权限/并发加固、视觉验收和部署**，不是第一次联调。 |

### 1.3 推荐顺序（总览）

```text
P0 准备与决策
  ↓
P1 基础设施 + 登录纵切
  ↓
P2 阶段 / 公告 / 主页面 / 待办纵切
  ↓
P3 实训室信息 + 文件纵切
  ↓
P4 志愿填报 + 分轮补录纵切
  ↓
P5 导师评分 / 同分 / 名额 / 发放纵切
  ↓
P6 学生拟录取确认 + 最终录取 + 超时纵切
  ↓
P7 统筹调剂结果 + 收尾
  ↓
P8 全链路验收 / 加固 / 部署
```

其中：

- P2 与 P3 在 P1 完成后可以并行。
- 每个纵切都必须包含：后端接口 + 前端页面 + 自动化测试 + 真实接口联调 + 手工验收。
- 前端最多比后端领先一个纵切，避免基于未实现契约做太多页面。

## 2. 推荐开发策略

### 2.1 契约先行

在写页面和接口前，先冻结：

- 数据库 v1（`schema.sql`、`data.sql`）
- API v1（30 个接口的路径、请求/响应、错误码、权限）
- 枚举与文案（`STUDENT/TEACHER/MANAGER`、`PENDING/CONFIRMED/ABANDONED` 等）

契约变更必须同步更新文档和前后端，不允许“代码先行、文档后补”。

### 2.2 走通骨架（Walking Skeleton）

第一个纵切不追求功能多，而是打通整条链路：

```text
浏览器 → Vite 代理 → Spring Boot → Session → MyBatis → MySQL → 返回统一响应
```

登录纵切完成后，后续每个业务纵切都复用这套骨架。

### 2.3 纵切开发，不做“大爆炸式联调”

每个纵切的标准闭环：

1. 后端接口 + 事务 + 权限 + 测试；
2. 前端页面 + 三态 + 表单禁用 + 防重复 + Toast；
3. 使用真实后端联调；
4. 手工验收 + 自动化测试；
5. 更新文档；
6. 合并主干。

### 2.4 测试随功能走

- 后端：每个 Service 规则至少一个集成测试；关键并发点单独测试。
- 前端：工具函数、Pinia store、表单校验用 Vitest；页面手工验收三态和禁用逻辑。
- 每轮迭代结束必须跑通：`mvn test`、`npm run lint`、`npm run build`。

## 3. 阶段依赖关系

```text
P0 准备
 └─> P1 登录纵切
      ├─> P2 阶段/公告/主页面/待办
      └─> P3 实训室/文件
            ├─> P4 志愿/补录（依赖 P2 阶段时间 + P3 文件/实训室）
            │     └─> P5 评分/名额/发放（依赖 P4 志愿目标 + P3 实训室名额）
            │           └─> P6 确认/最终录取/超时（依赖 P5 拟录取）
            │                 └─> P7 调剂结果（依赖 P6 最终录取 + P2 阶段结束）
            └─> P8 全链路验收/加固/部署（依赖全部）
```

**关键路径**：P0 → P1 → P3 → P4 → P5 → P6 → P7 → P8。  
P2 不在关键路径上，但 P4 依赖 P2 的阶段时间判断，所以 P2 不能晚于 P4 太多。

## 5. 并行开发与关键路径

### 5.1 单人开发

按 P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8 顺序做，每个纵切完成后立即联调，不攒到最后。

### 5.2 两人（1 前端 + 1 后端）

- P0：一起定契约。
- P1：后端做登录；前端做脚手架、布局、登录页；P1 末联调。
- P2：后端做阶段/公告/待办；前端做主页/公告/待办/阶段页；P2 末联调。
- P3：后端做文件/实训室；前端做上传/实训室页面；P3 末联调。
- P4~P7：按纵切交替推进，前端最多领先后端一个纵切。
- P8：一起回归、修问题、部署。

### 5.3 四人（2 前端 + 2 后端）

- P1 完成后，按纵切分配：
  - 后端 A：P2 阶段/公告/待办 → P4 志愿 → P6 确认/最终录取。
  - 后端 B：P3 文件/实训室 → P5 评分/发放 → P7 调剂。
  - 前端 A：登录/布局 → P2 主页/公告/待办/阶段页 → P4 志愿页。
  - 前端 B：公共组件 → P3 实训室/文件 → P5 发放页 → P6 确认页。
- 每个纵切必须有前后端共同负责人，避免“前端做完扔给后端”。
- 集成分支每天合并，禁止长期分叉。

### 5.4 关键路径与卡点

| 卡点 | 影响 | 提前动作 |
| --- | --- | --- |
| P0 业务决策未定 | 数据库/接口返工 | 第一周内签字确认 |
| P2 阶段时间未完成 | P4 志愿窗口、P5 发放、P6 确认都受影响 | P1 后优先做 P2-B01/B02 |
| P3 文件上传未完成 | P4 志愿无法提交、P5 无法看简历 | P1 后尽早做 P3-B01/B02 |
| P3 实训室名额未完成 | P5 发放、P4 补录剩余名额无法计算 | P3-B03/B04 优先 |
| P5 发放未完成 | P6 确认没有数据 | P5 先跑通最小发放链路 |
| P6 最终录取未完成 | P7 调剂、主页面已录取状态无法验收 | P6-B02/B03 优先 |
| 契约漂移 | 前后端反复改 | P0 冻结 + 每纵切接口评审 |

## 9. 完成定义（DoD）

每个子任务完成时至少满足：

- [ ] 与对应需求文档、原型、数据库/API 设计一致。
- [ ] 后端完成会话校验、角色校验、数据归属校验。
- [ ] 核心业务不变量在 Service/数据库强制，不依赖前端。
- [ ] 接口符合 `/api/v1`、统一响应、错误码、分页、时间格式。
- [ ] 前端有加载/空/失败三态，表单禁用逻辑正确，提交防重复，文案一致。
- [ ] 视觉与原型主题一致，复用公共布局和组件。
- [ ] 新增/修改接口与表结构已同步 `docs/design/`。
- [ ] 后端测试覆盖关键规则；`mvn test` 通过。
- [ ] `npm run lint`、`npm run build` 通过。
- [ ] 无硬编码身份、演示数据、密码、绝对路径；无 `console.log` / `debugger`。
- [ ] 任务对应页面/流程已用真实接口联调并手工验收。

## 10. 范围边界提醒

开发中不要越界实现：

- 不做注册、密码登录、找回密码。
- 不做真实人脸识别，不采集/存储人脸数据。
- 不做公告新增/编辑/删除，公告只能由阶段保存生成。
- 不做线上调剂确认、导师线上接收调剂；调剂线下进行，线上只展示结果。
- 不做短信、邮件、站内推送；“发放拟录取”只生成系统内记录。
- 不做第四轮填报。
- 不做宣讲、开放日、面试的线上排期/签到。
- 不做角色切换和原型演示开关。
- 不把 `uploads/` 映射为静态资源。
- 不用 `localStorage` 中的角色/学工号做鉴权。
- 名额/确认/发放不能只靠前端置灰，必须事务 + 唯一索引 + 状态判断。
