## 0. 先回答：接下来就是前端、后端、联调、测试、上线吗？

**是，最终交付就是这五类工作；但不是五个先后阶段。**

正确的工作方式是**纵切闭环**：

```text
定契约 / 搭环境
  → 选一个业务纵切
      → 后端接口 + 业务规则 + 事务 + 权限 + 测试
      → 前端页面 + 加载/空/失败三态 + 表单禁用 + 防重复
      → 使用真实后端联调
      → 自动化测试 + 手工验收
      → 同步文档 + 合并
  → 下一个纵切
  → 全部纵切完成后：全链路回归、安全/并发/时间/文件审计、部署上线
```

因此：

- 前端、后端不是“全部写完再联调”；
- 联调不是最后一个阶段，而是每个纵切都做；
- 测试随每个纵切走，不攒到最后；
- 上线是 P8，只做全链路回归、加固、验收和部署。

## 1. 冻结前提与实现口径

### 1.1 不再改变的内容

- 需求：`docs/requirements/` 已冻结，不新增、删减或改写业务规则。
- 范围边界：
  - 不做注册、密码登录、找回密码；
  - 不做真实人脸识别，只做前端模拟比对；
  - 不做公告新增/编辑/删除，公告只能由阶段保存时生成；
  - 不做线上调剂确认、导师线上接收，调剂线下进行、线上只读；
  - 不做短信、邮件、站内推送；
  - 不做第四轮填报；
  - 不做宣讲、开放日、面试的线上排期/签到；
  - 不做角色切换和原型演示开关；
  - 不把 `uploads/` 映射为静态资源；
  - 不用 `localStorage` 中的角色/学工号做鉴权。
- 技术栈：
  - 前端：Vue 3 + Vite、Vue Router 4、Pinia、Axios、原生 CSS；
  - 后端：Java 17、Spring Boot 3.3.x、Maven、原生 MyBatis XML；
  - 数据库：MySQL 8.0+、InnoDB、utf8mb4；
  - 鉴权：HttpSession + Cookie，不引入 Spring Security；
  - 接口：`/api/v1`、统一响应 `{code, message, data}`。

**目标**：把契约、环境、测试基座准备好，能开始第一个纵切。

**任务**

   - 旧目录 `docs/接口设计/`、`docs/数据库设计/` 保留跳转说明；
   - 统一接口命名（D8）。
2. 冻结数据库 v1：
   - `backend/src/main/resources/db/schema.sql`；
   - 7 行 `stage` 种子；
   - 阶段保存的“已截止不得延长”校验规则（D3，不加字段）；
   - 唯一索引、逻辑外键、检查约束；
   - dev 用 `data.sql`。
3. 准备测试数据与 reset：
   - 1 名负责人、4 名导师、10 名学生；

   - 1 条调剂最终录取样例；

4. 后端脚手架：
   - Maven + Spring Boot 3.3.x + Java 17；
   - 包结构按 `common/config/auth/user/stage/announcement/lab/volunteer/offer/admission/file/todo`；
   - 统一响应、异常、Clock、Jackson、Session 配置占位。
5. 前端脚手架：
   - Vue 3 + Vite + Router + Pinia + Axios；
   - `api/router/stores/layouts/views/components/styles/utils`；
   - 白橙主题变量（D1）、基础样式、字体自托管。
6. 本地环境与 CI：
   - JDK 17、Maven 3.9+、Node ≥18、MySQL 8；
   - 开发库 + 独立测试库；
   - Vite 代理 `/api`；
   - CI 执行 `mvn test`、`npm ci`、`npm run lint`、`npm run build`。
7. 启动验证：
   - 后端 `mvn spring-boot:run` 可启动；

   - `schema.sql` 可在 MySQL 8 执行；
   - `data.sql` 可加载；
   - 健康检查可访问。

**P0 出口**：契约冻结、数据库可执行、种子数据可用、前后端能启动、CI 能跑通空项目构建。

### P1 — 登录纵切（5–7 人日）

**目标**：打通浏览器 → Vite → Spring Boot → Session → MySQL 的完整链路；三角色能登录、看到对应菜单、注销。

**后端**

- `Result`、`PageResult`、`ErrorCode`、`BusinessException`、`GlobalExceptionHandler`；
- `WebMvcConfig`、`AuthInterceptor`、`CurrentUser` 解析器 / `SessionUserHolder`；
- `User`、`UserMapper` XML、`UserService`；`(staff_no, role)` 唯一；首次登录自动创建；
- `POST /auth/login`、`POST /auth/logout`、`GET /auth/me`；
- 销毁旧会话并新建会话；记录登录日志；
- `GET /health`；
- 登录/会话/角色路径测试。

**前端**

- 应用骨架、路由、Pinia；
- `request.js`：`baseURL=/api/v1`、`withCredentials`、统一 Toast、401 清状态跳登录、403 提示、网络异常提示；
- `useUserStore`：`fetchMe()`、`login()`、`logout()`；
- 路由 `meta.roles` 守卫；刷新恢复会话；未登录跳 `/login?redirect=...`；
- 登录页：角色三选一、学工号、模拟人脸比对、格式校验“学工号异常”、比对成功后锁定输入框；
- `LoginLayout`、`DefaultLayout`、`AppSidebar`、`AppHeader`；
- `ToastHost`、`BaseModal`、`EmptyState`、加载态。

**联调/验收**

- 三个角色真实登录、菜单正确；
- 刷新保持会话；注销回登录页；
- 未登录访问受保护路由跳登录；
- 角色不符返回 403；
- `npm run lint && npm run build` 通过。

**P1 出口**：登录纵切端到端可用，后续所有纵切复用该骨架。

### P2 — 阶段 / 公告 / 主页面 / 待办纵切（7–10 人日）

**目标**：负责人配置 7 个阶段并可发布公告；全体用户看到当前阶段、公告和个人待办。

**P2a：阶段与公告（阻塞，先做）**

- `GET /stages/current`：当前阶段、空档、结束、未配置、`serverTime`；
- `GET /manager/stages`、`PUT /manager/stages`：7 行完整、起止、顺序、不重叠校验；`changeNo` 幂等；
- `stage_change`、公告草稿、独立事务发布、失败标记；
- `POST /manager/stages/announcement`：只重试公告，不重复保存阶段、不重复生成公告；
- `GET /announcements`、`GET /announcements/{id}`、`GET /manager/stage-changes`；
- 阶段保存校验：已截止阶段的 `end_at` 不得改到未来，否则提示“阶段已截止，不能延长”；
- 阶段/公告/待办框架测试。

**P2b：页面（可与 P3 并行）**

- 主页面：步骤条、当前阶段/空档/结束/未配置、倒计时、公告摘要、待办摘要；
- 公告页：列表分页、详情、暂无公告、加载失败重试；无新增/编辑/删除；
- 个人待办页：按角色展示、截止时间、状态、前往办理；空状态与失败态区分；
- 阶段管理页：7 行时间编辑、完整性/起止/顺序/重叠提示、发布公告开关、自动生成标题正文、保存/失败重试；
- `StepBar`、`Countdown`、`StatusBadge`；基于 `serverTime` 计算偏移；
- 待办规则矩阵：角色 × 阶段 × 用户状态 × 截止时间 × `actionPath`（D4/D5）。

**联调/验收**

- 负责人保存阶段并发布公告 → 学生/导师刷新看到新阶段和公告；
- 重复点击不重复生成；公告失败可重试；
- 阶段截止后尝试延长，保存被拒绝，旧窗口不重新开放；
- 主页面、公告页、待办页、阶段管理页手工验收。

**P2 出口**：阶段、公告、待办全部真实接口可用；公告失败重试可用。

### P3 — 实训室信息 + 文件纵切（5–8 人日）

**目标**：导师提交/修改本人实训室信息和 PDF 简历；学生查看列表/详情并鉴权下载简历。

**后端**

- `resume_file` 模型/Mapper；
- PDF 扩展名、Content-Type、`%PDF-`、大小校验；UUID 磁盘名；失败不留半条记录；
- `GET /files/{id}`：导师简历全员可读；学生简历本人/收到申请的导师可读；
- `GET/PUT /teacher/lab`：必填、正整数、本人唯一、名额不得低于当前占用；
- `QuotaService`：统一计算 `admitted + pending` 占用；P3 使用真实 `final_admission` / `offer` 表计数（dev 种子已有数据）；
- `GET /labs`、`GET /labs/{id}`：关键字/研究方向/分页/研究方向选项/实训室总额。

**前端**

- `FileUpload`：仅 PDF、上传中/成功/失败、替换、返回 `fileId`；
- 提交实训室信息页：回显、必填、正整数、名额下限、PDF、提交中禁用、失败保留；
- 查看实训室信息页：卡片列表、筛选、详情弹窗、简历下载、空/失败态。

**联调/验收**

- 导师提交 → 学生列表/详情可见 → 简历下载；
- 修改后学生看到更新；
- 非 PDF、超限、越权下载被拒；
- 名额低于占用被拒。

**P3 出口**：导师信息可提交/修改；学生可查看和下载；文件安全校验通过。

### P4 — 志愿填报 + 分轮补录纵切（7–10 人日）

**目标**：学生按轮次提交/重填 1–3 名导师志愿、两项调剂意愿和 PDF 简历；第二、三轮展示剩余名额导师并允许再次填报。

**后端**

- `volunteer_application`、`application_target` 模型/Mapper；
- `GET /student/volunteers/current`、`GET /student/volunteers`、`GET /student/available-teachers`；
- `POST /student/volunteers`：
  - 轮次时间、已录取、导师姓名去空格/合并空格后唯一匹配；
  - 1–3 名、不重复、调剂意愿必填、简历归属；
  - 第二/三轮补录名额校验；
  - 本轮目标替换、行锁、事务。
- 志愿规则测试：1–3 名、空白、重复、缺调剂意愿、非开放时间、已录取、补录无名额、导师不存在/重名、简历不属于本人。

**前端**

- 志愿填报页：三个普通姓名输入框、重复校验、两项调剂意愿、PDF、提交按钮启用/禁用、提交中防重复、失败保留；
- 补录页：由当前阶段 `ROUND_2` / `ROUND_3` **自动决定**，不做手动“补录模式”开关；顶部只读剩余名额导师；仍使用三个输入框；
- 当前/历史志愿展示：本轮回显、历史轮次只读、三态。

**联调/验收**

- 第一轮提交 → 第二轮补录 → 历史不覆盖；
- 已录取/未开放/无名额/重名提示正确；
- 导师端能看到投递到本人的目标。

**P4 出口**：志愿提交/重填真实可用；补录页只读导师列表正确；异常文案与需求一致。

### P5 — 导师评分 / 同分 / 名额 / 发放纵切（10–14 人日）

**目标**：导师查看本人名下申请、录入分数、处理同分、查看名额概览，并按分数/分数线/名额发放拟录取。

**后端**

- `GET /teacher/applications`：本人名下/当前轮、学生信息、简历、分数、同分顺序、拟录取状态、学生是否已录取；支持 `roundNo` 历史只读；
- `PUT /teacher/applications/{id}/score`：0–100、本人归属、轮次开放、已发放锁定、修改后清空同分顺序；
- `PUT /teacher/applications/{id}/order`：正整数、同分组内不重复、已发放锁定、必须已评分；
- `GET /teacher/admissions`：计划名额、最终录取数、未过期待确认数、剩余名额、`canGrant`；
- `POST /teacher/admissions/grant`：
  - 锁 `lab_info`，计算占用；
  - 候选：已评分、分数 ≥ 分数线、学生无最终录取、该目标无 offer、同分已定序；
  - 按 `score DESC, tie_order ASC, id ASC` 插入 `PENDING`；
  - `confirmDeadline = 本轮 end_at`；
  - 名额满即停；不超发；重复发放由唯一索引兜底；
  - 截止后不发放/不递补。
- 测试：分数线、未评分、同分未定序、名额满、无达标、重复发放、截止、释放后递补、并发不超发。

**前端**

- 发放拟录取页：名额概览、申请表格、分数输入、排序、同分顺序、录取分数线、简历查看；
- 发放交互：按钮启用/禁用、提交中禁用、名额满/无达标/同分未定序/已截止 Toast；
- 简历查看：弹窗或新窗口下载；无权限提示。

**联调/验收**

- 评分 → 排序 → 设置分数线 → 发放 → 名额占满/递补；
- 并发重复点击不重复发放；
- 所有提示文案正确。

**P5 出口**：导师可完成评分、同分排序、发放和递补；名额不超发；重复操作不重复生成。

### P6 — 学生拟录取确认 + 最终录取 + 超时纵切（7–10 人日）

**目标**：学生查看本人拟录取，确认一条后形成最终录取，其余自动放弃；截止未确认自动放弃；主页面显示已录取。

**后端**

- `GET /student/offers`：本人、状态、截止时间、`canConfirm`；返回前惰性校正超时；
- `POST /student/offers/{id}/confirm`：
  - 本人、`PENDING`、未截止、无最终录取；
  - 确认一条、其余放弃、插入最终录取；
  - 行锁 + `final_admission(student_id)` 唯一索引兜底。
- `GET /student/admission`：志愿/调剂类型、导师/实训室；未录取返回 `admitted=false`；
- 超时任务 + 读取/确认惰性校正：`PENDING` 且过截止 → `ABANDONED/TIMEOUT`；已确认不受影响；
- 测试：唯一确认、重复请求、截止拒绝、超时自动放弃、确认其他导师、已确认不受影响、并发只产生一个结果。

**前端**

- 拟录取确认页：卡片、状态、确认截止倒计时、确认按钮、二次确认弹窗、空状态、失败刷新提示；
- 最终录取与主页面：最终录取展示、已录取横幅、志愿填报菜单点击提示“已被录取！”、待办不再生成；
- 调剂结果只读展示，无确认按钮。

**联调/验收**

- 发放 → 学生确认 → 最终录取 → 其他拟录取放弃；
- 超时后释放名额并可递补；
- 主页面状态正确。

**P6 出口**：学生只能确认一个；最终录取唯一；超时自动放弃；教师端能继续递补。

---

### P7 — 统筹调剂结果（2–3 人日）

**目标**：三轮结束后展示线下调剂结果；调剂录取不需要学生确认；已录取学生不能继续填报。

**任务**

- 调剂结果导入脚本/初始化 SQL：写 `final_admission` 调剂类型；
- 校验：学生无最终录取、无遗留待确认、名额充足、唯一约束；
- `GET /student/admission` 返回调剂类型；
- 已录取学生提交志愿/补录被拒绝；
- 页面只读展示调剂结果，无确认按钮；
- 测试：重复导入不重复、名额不足拒绝、已有录取拒绝、调剂结果只读。

**P7 出口**：调剂结果只读展示；不出现线上确认/导师接收；学生最终去向唯一。

### P8 — 全链路验收 / 加固 / 部署（7–10 人日）

**任务**

1. 权限矩阵回归：三角色交叉访问、越权读写、文件越权下载、路径角色 + 数据归属双重校验。
2. 并发测试：并发发放、并发确认、重复点击保存阶段、重复发布公告；不超发、不重复确认、不重复公告。
3. 时间与截止测试：可控 `Clock` 覆盖开放前/开放中/截止后、空档、全部结束、阶段调整不回滚、已截止阶段延长被拒绝。
4. 前端状态审计：每页加载中/空/失败三态；表单禁用/启用；提交防重复；Toast 文案；失败不显示为空。
5. 视觉对齐原型：白橙配色、侧边栏 238px、卡片层级、字体、按钮状态、表格/徽标/倒计时；窄屏纵向滚动。
6. 文件安全复核：扩展名、MIME、文件头、大小、UUID 路径、路径穿越、非静态目录、鉴权下载。
7. 日志与敏感信息：登录、提交志愿、发放、确认、阶段保存有日志；不记录 Session ID、简历全文、人脸数据；移除 `console.log` / `debugger`。
8. 文档同步：`docs/design/api.md`、`db-schema.md`、`architecture.md` 与代码一致。
9. 全量构建：`cd backend && mvn test`；`cd frontend && npm run lint && npm run build`。
10. 手工验收：按页面/角色/流程逐项验收，记录问题并回归。
11. 部署配置：
    - 生产同源部署：Nginx 托管 `frontend/dist`，`/api` 反代后端；
    - 环境变量、上传目录、数据库、Session、时区 `Asia/Shanghai`；
    - HTTPS、`Secure` Cookie、备份目录、日志轮转；
    - 部署后冒烟：登录、阶段、公告、上传、下载、退出。
12. 最终评审：对照 DoD 和需求验收要点逐项确认；遗留问题清单。

**P8 出口**：全部自动化测试和构建通过；权限/并发/时间/文件安全回归通过；手工验收无阻塞问题；文档与代码一致；可部署。

## 3. 每个纵切固定做的五件事

| 顺序 | 动作 | 验收要点 |
| --- | --- | --- |
| 1 | 后端 | Controller 只收参/校验/返回；Service 写业务规则、事务、归属；Mapper 只写 SQL；DTO 不返回实体 |
| 2 | 前端 | API 封装在 `src/api/*.js`；页面三态；表单禁用/启用；提交防重复；失败保留内容；Toast 文案 |
| 3 | 联调 | 用真实后端，不用 mock；覆盖 401/403/404/409/500；确认 Cookie 携带 |
| 4 | 测试 | 后端集成测试覆盖规则；前端 `lint/build`；页面手工验收；关键并发点单独测 |
| 5 | 文档/合并 | 同步 `docs/design/`；移除调试输出；按 Conventional Commits 合并 |

## 7. 完成定义（DoD）

每个纵切完成时至少满足：

- [ ] 与对应需求文档、原型、数据库/API 设计一致。
- [ ] 后端完成会话校验、角色校验、数据归属校验。
- [ ] 核心业务不变量在 Service/数据库强制，不依赖前端。
- [ ] 接口符合 `/api/v1`、统一响应、错误码、分页、时间格式。
- [ ] 前端有加载/空/失败三态，表单禁用逻辑正确，提交防重复，文案一致。
- [ ] 视觉与白橙原型一致，复用公共布局和组件。
- [ ] 新增/修改接口与表结构已同步 `docs/design/`。
- [ ] 后端测试覆盖关键规则；`mvn test` 通过。
- [ ] `npm run lint`、`npm run build` 通过。
- [ ] 无硬编码身份、演示数据、密码、绝对路径；无 `console.log` / `debugger`。
- [ ] 任务对应页面/流程已用真实接口联调并手工验收。

> 脚手架/决策类任务只要求“可启动、可验证、文档一致”，不套用完整业务 DoD。
